# Context: kata

Kata launches headless coding-agent jobs and watches each to the end. An engineer describes a job once, in a run-spec: what to do, where, which skills the agent may use, and the limits it runs under. Kata then runs that same description the same way on a laptop, on a teammate's machine, or in CI. Kata does not build its own agent. It drives Claude Code in its non-interactive mode and controls everything around it: what the agent starts with, what it is told it is for, which skills it gets, and when to stop it. Before a run starts, the engineer can see everything the agent will be given and switch parts of it off for that run. While it runs, the operator can send the agent messages to correct its direction without cancelling it. Three consumers depend on it: the Workbench desktop app (for engineers), the Shokunin orchestrator (which runs many jobs), and CI pipelines. All three go through the same `kata` program. The Workbench also has a second mode, AI-SDLC, which is a set of screens over the hoshin plugin's workflow. The plugin decides where each change stands and what may happen next. It starts a change with its branch and its own copy of the master repository, commits each acceptance, prepares each repository for its build, runs the team's checks (whose results on the base the engineer can follow, and settle a known failing one, from the Workbench), and declares the change done by pushing and opening pull requests. A system is laid out either as a workspace (a master repository beside its product repositories) or as a single repository that holds its own records and is divided into apps; Kata itself is the second kind. Every workflow step can be stopped by the engineer, and none is cut off by a fixed time. Kata asks the plugin, shows the answer, and carries out what the engineer picks through the plugin. Kata keeps what the plugin does not do: running and watching the agents, the limits and permissions they run under, the view of what changed, the links between a task and the runs that worked on it, and the screens. Several changes, in one system or several, can be worked on and built at the same time, as long as no two builds need the same product repository. The AI-SDLC home is for what is in flight: it shows one system at a time, lists that system's open changes first and keeps finished changes in a folded section. A line along the bottom of every screen shows which version of the Workbench and of the hoshin workflow this machine runs. A workspace set up with the earlier ai-sdlc workflow is offered a migration to hoshin from the home page.

## Domain terms

| Term | Meaning in this business |
|---|---|
| Kata / run-spec | One saved, reproducible description of an agent job: task, working folder, skills, limits, permission posture. |
| Run | One execution of a run-spec, from start to a single final outcome. |
| Empty room | Starting the agent with none of the engineer's personal settings or skills loaded, so a run behaves the same on any machine. On by default. |
| Retasking | Telling the agent what it is for in this job, by adding to or replacing its standing instructions. |
| Kit | The exact set of skills and plugins a run is given, assembled fresh for that run and thrown away afterwards. |
| Leash | The limits on a run: turn cap, wall-clock time, spending ceiling, and optional isolation of its file changes. |
| Outcome code | The number a run ends with, which tells CI or an orchestrator why it ended (finished, out of time, out of budget, nobody answered, cancelled). |
| Bundle | A self-contained folder holding a run-spec plus copies of every skill it needs, so it runs on a machine with nothing installed. |
| Operator | The person (or program) watching a run who can answer the agent's questions, approve or refuse its actions, and send it messages. |
| Steering / operator message | A message the operator sends a live run. The agent reads it before its next step and carries on. A run that took at least one message is a steered run. |
| Permission posture | How the agent's requests to use tools are approved: skipped entirely, decided by written rules plus the operator, or decided by Claude's own safety classifier. |
| Worktree isolation | Running the agent on a separate copy of the repository's branch, so its edits do not touch the engineer's working files. |
| Given | Everything a run starts with besides its task: hooks, skills, plugins, standing instructions and tool servers, each from a named source (personal, project, project-local, plugin, organization, Kata, run-spec). |
| Switch off | Leaving one given item out of one run. The run-spec records only the items switched off. |
| Lock | A reason a given item cannot be switched off, shown with the item. |
| Start report | What Claude says it actually loaded when a run starts. Kata compares it with what was asked for. |
| Workspace (AI-SDLC) | A folder of git repositories side by side. Exactly one is the master repository holding intents, specs and plans. The others are product code. |
| Single-repo layout | A system that is one repository holding its own intents, specs and plans next to its code. The repository is its own master and has no product repositories beside it. |
| App | One part of a single-repo system, living in its own folder of the repository. Apps take the place of product repositories: each has its own context file, tasks, build session, checks and findings. |
| Change (AI-SDLC) | One piece of product work, tracked as a folder of intent, spec and plan documents, each accepted in turn. |
| Change copy | A change's own copy of the master repository, on the change's branch, made by the plugin when the change starts. The change's documents are written and committed there, so the engineer's own checkout and other changes are not disturbed. Changes started before copies existed live in the engineer's checkout. |
| hoshin program | The plugin's own program, which Kata asks every workflow question (where a change stands, what it offers) and through which it starts, renames, accepts, builds and declares done. It also reads and checks the documents. |
| Track | Which way a change runs: the full pipeline, or the light track for a fix. |
| Triage | The run that reads a short description of a change and proposes which track it takes. |
| Fix | A change on the light track: one repository, no business rule changes, at most three tasks. One run writes a short intent, spec and plan, and the engineer accepts them once. |
| Layout | The version of a document's format. Older layouts are still read and are labelled as older. |
| Leftovers | What a stopped or failed AI-SDLC document, triage or fix run left behind (new commits, changed files), shown to the engineer before anything is thrown away. |
| Build | Carrying out an accepted plan: one agent run per repository, each working only on the plan's tasks for that repository, followed by one review of the whole change. A change has at most one build at a time. |
| Hold | A product repository taken by one change's build or review for as long as it runs. Another change that needs it waits and is told which change holds it. |
| Task | One numbered step of the plan, assigned to one repository, optionally depending on tasks that must be finished first. |
| Build log | The record of finished tasks, one per repository, kept in the master repository. A task is finished only when its entry is committed there. |
| Departure | What a finished task did differently from the plan, written in the task's build log entry. The plan itself is never edited. A commit that names no task also shows as a departure. |
| Change branch | The branch a change's work lives on, with the same name in every repository it touches. In a system with no team naming it is `change/` followed by the change's folder name. With team naming it comes from the team's pattern. The plugin creates it when the change starts and records it in the change record. |
| Change record | The committed file in a change's folder (`change.yml`) holding its branch, work type, scope, base branch and the pull requests opened for it. Written only by the plugin. Older changes have a branch record (`branch.md`) instead. |
| Team naming | A system's shared patterns for change branch names and pull request titles, built from the change's work type, scope, name and title. It is kept in the master repository's marker on its base branch, so every engineer gets the same setting. |
| Work type | The kind of work a change is (feat, fix, docs and the other conventional commit types), picked when the change starts. It names the branch and the pull request title only; each commit keeps the type that fits its own work. |
| Round | Another set of build runs after a build has stopped or finished: one agent per chosen repository at once, each told which review findings to fix and any note the engineer wrote. |
| Review | One independent look at the whole change across all repositories once every task is finished. It reports findings and changes no product code. |
| Review document | The change's committed record of every review: which commits each one covered and its findings, each with a severity, a repository and a concern (spec, bug or convention). |
| Team checks | Commands a team commits with its hoshin settings in the master repository. The plugin runs them when a repository's build finishes and again before declaring done. They replace the per-machine checks files. |
| Checks on the base | The team checks run on the base commit when a build starts, before the first task, so that a failure already on the base does not block the build at finish. The plugin keeps their results on this machine. |
| Accepted check | A check that fails on the base without saying what failed, which the engineer accepted for this change, this repository and this base commit, so it does not block the build at finish. Only the engineer can accept one, one at a time, on this machine only. |
| Declare done | The engineer's final step: the plugin verifies the change, pushes every touched repository and opens one pull request per touched repository. |
| Open change | A change that is still in flight. The AI-SDLC home lists open changes first, by name and title at once, with each one's stage and actions filling in a moment later. |
| Finished change | A change the hoshin workflow says is over: merged or rejected. The home keeps these in a folded "Finished (n)" section, newest first, each marked merged or rejected. |
| Merge check | The question whether every pull request of a change declared done is merged on GitHub and its copy can be removed. It decides whether the home row reads "merged, remove the copy". |
| Session (build page) | One agent run in one repository of a build. A repository can have several (the first run, a continue, a round). The running one keeps the full height; each earlier one is a tab that says how it ended. |
| Version line | The line along the bottom of every screen: the Workbench's version and the hoshin workflow's version on this machine. Clicking it copies both as plain text for a bug report. |
| Running changes | The entries in the Workbench's top bar for every change with a live run, a stopped repository, a held build or a waiting review, in any system, each opening that change's sessions. |
| Progress line | A line naming a slow step while it runs, which says so when the step takes much longer than usual. |
| Workflow step | Work the plugin does for the engineer on a change: starting it, renaming it, removing its copy, accepting or rejecting a document, preparing a build or review, and declaring done. Each can be stopped. |
| Observed red | Whether a task's failing test was actually seen to fail before the fix, as the task's build log entry records it: observed, not observed (with a reason), not recorded, or unreadable. |
| Migration | Moving a workspace set up with the earlier ai-sdlc workflow to hoshin's names, done by the plugin from the Workbench's home page. |

## What users can do today

- **Engineer (command line):** create a starter run-spec, check a run-spec for mistakes without running it, list the skills and plugins available, run a job and read its live event stream, and package a job as a portable bundle.
- **Engineer (Workbench, run mode):** compose a run-spec with a form, pick skills from what is installed, preview everything the run will be given and its settings with where each comes from, switch given items off for one run or a saved job, run it and watch it live, send the agent messages while it works and see when each was read, see afterwards whether Claude honored each switch, answer the agent's questions, approve or refuse its actions, cancel it, save jobs to a library, rerun a saved job with a fresh task, keep reusable context snippets, and browse past runs, where a steered run is marked, how each run ended is recorded, and its transcript shows each message with when it was sent and read.
- **Engineer (Workbench, AI-SDLC mode, home):** open a workspace or a single-repo repository (the repository folder, a folder inside it, or its parent), migrate a workspace set up with ai-sdlc to hoshin after reviewing what will change, open the workspace they used last, see the system they used last in it (switching systems is remembered), see every open change at once by name and title with its stage and actions following, unfold a Finished section of merged and rejected changes, see which declared changes have merged and offer to remove their copy, open any change so that its page reads that change alone, and keep a New change description safe (a click outside it or Escape does not close it; only Cancel does, and discards the text).
- **Engineer (Workbench, AI-SDLC mode, documents):** open a workspace, run first-time setup, write or refresh the workspace instructions, read each repository's (or app's) business context file and start or refresh it from there, describe a new change and let the workflow pick its track (or go straight to the full pipeline, picking a work type and scope), have the agent draft the intent, spec and plan in the change's own copy, accept or reject each document, reopen an accepted document (including the intent or spec after a build has started), draft, change, accept or reopen a fix, move a drafted fix to the full pipeline, rename the change's branch, choose how document runs are approved (Claude's classifier by default), preview and adjust each run's settings, send messages to a live run, see the change's copy and open its folder, remove the copy once its pull requests are merged, stop any workflow step while it runs, and review and discard what a stopped document run left behind.
- **Engineer (Workbench, AI-SDLC mode, build):** accept the plan, start the build with a time limit they can change, watch, answer and send messages to each repository's agent separately, read an earlier session of a repository from its tab (which says how it ended) while the running session keeps its full height and flags a waiting question, see which repositories are working, waiting, stopped or held by another change, continue a stopped repository, start another round from picked review findings with a note per repository, stop a build's preparation, read the task list with finished tasks folded and filtered (all, open, departed, done), each task's test and compile commands and whether its failing test was observed (with the stored output where it was not), and the review's findings grouped by repository or app, jump to each finding's file, arrange the build page into areas per mode, browse what changed in every repository, see each repository's team checks as the plugin last ran them, follow the checks on the base while a build starts (the running check, how many are done, each result), read a failed check's output, accept a check that fails on the base for this build, run the checks again after one failed at finish, declare the change done with a progress line per step, see the pull requests and their state, and open each one in their default browser.
- **Engineer (Workbench, several changes):** leave a building change, open and work on another change in any system, start its build when its repositories are free, follow every change with activity from the top bar, counted by kind, and reach a run waiting on them in one step, and be asked before closing the Workbench while anything is running.
- **Orchestrator or CI:** run a job by spawning `kata`, read its events, answer, send messages or cancel through its input, and branch on its outcome code.

## Rules the system enforces

Each rule carries one provenance tag: `seen in code`, `confirmed by engineer`, or `intent unknown`.

## Systems and integrations

- **Claude Code:** the agent that does the actual work. Kata starts it, feeds it instructions, skills and limits, and reads its live output and start report. It must be installed and logged in. Kata also reads Claude's own setup (personal, project, local and organization settings, installed plugins) to list what a run is given. The task reaches Claude as the first message on its input, so later messages can follow (C90). The kit reaches Claude as up to two plugin folders, one for the skills a run carries and one for the plugins. Kata needs version 2.1.311 or later (C91).
- **hoshin plugin:** owns the AI-SDLC workflow, including which layout a folder has and which apps a single-repo system holds. Kata asks its program for every workflow answer and carries out every workflow step through it: starting, renaming and removing changes and their copies, committing acceptances and rejections, preparing repositories for a build, recording checks, base check results, accepted checks and observed red, migrating ai-sdlc workspaces, and declaring done. Its skills, including its review skill, run inside each agent's session, with its gate and guard. Kata needs version 1.1.0 or later (C158) and is tested against a vendored copy of the program. It replaced the ai-sdlc plugin, which Kata no longer drives except to migrate from it (C155).
- **Node.js:** 22.18 or later, needed to run the plugin's program. Without it the AI-SDLC mode offers nothing.
- **Git repositories:** Kata reads them itself for worktree isolation, run change summaries, the view of what changed, the task links and the leftovers of a stopped run, and still switches the master checkout's branch (workspace layout only) and discards leftovers itself. Every other AI-SDLC branch, commit and push is the plugin's, through the git program, which must be installed for the AI-SDLC mode.
- **GitHub:** the plugin pushes and opens pull requests through GitHub's command-line tool under the engineer's own sign-in, and reports their state. Kata talks to GitHub only through the plugin and stores no credential. Agents are denied GitHub's command-line tool.
- **Shokunin orchestrator:** a separate .NET product that writes run-specs and runs them through `kata`, reading the event stream. Integration is planned, not finished.
- **CI pipelines:** run jobs unattended and branch on the outcome code.
- **Kata's local data folder:** holds saved jobs, run history transcripts (with how each run ended), the saved workspaces and single-repo repositories with each one's layout, when it was last opened and the system last shown in it, context snippets, isolated worktrees, Workbench settings, the build page arrangement, saved format answers, per-run private folders, the links between a change, its tasks and its runs, and, read only, the old per-machine checks files and pull request records. Change copies live in the workspace, not here.

## Known oddities

- The tests that prove switch-off against a real Claude are opt-in, and some edit the engineer's real Claude setup, so CI skips them. Two proofs that need an API key (what the empty room loads, and a trivial real run) were not re-run on 2.1.311. The proof that the plugin's gate and guard fire under Kata's own invocation is also opt-in. (seen in code)
- Catalog discovery falls back to the current folder when no home folder is known, and does not de-duplicate a skill installed both personally and in the project. Both are on the roadmap backlog. (seen in code)
- File rename line counts in a run's change summary are reported as zero. Tracked as issue #7. (seen in code)
- Switching off a project hook is not fully faithful (C75): the project's skills, agents and commands reappear under a "kata-proj" prefix, project tool servers report a different source, standing instructions in subfolders are lost, and imports inside copied instruction files are not followed. (seen in code)
- Shell writes into another repository or another change's copy are not denied. The deny rules apply to Claude's editing tools only, and shell writes fall to Claude's classifier; the plugin's guard covers only its own files and pushes. The engineer says this is a known gap and wants a stricter boundary later. (confirmed by engineer)
- When no run of a build is live, a stopped build offers "Start build" instead of "Continue build", and continuing one repository restarts every repository that needs work and can run an already finished round again, because the round requests are never cleared. The engineer says both are bugs; C39 is the intended rule. (confirmed by engineer)
- A review started by hand, or a continue, in a session with no build (for example after restarting the Workbench) gets one hour instead of the build's limit. The engineer says this is a bug (C116). (confirmed by engineer)
- A review started by hand while the committed review is already current launches nothing, though the action is offered. (seen in code)
- The first triage run, which starts before a change exists, can edit Kata's saved format answers, although C66 promises it a build run's limits. The engineer called this a bug when it also covered fix runs; fix runs now carry the deny. (confirmed by engineer)
- The first triage run also carries no deny on the engineer's checkout of the master or on other changes' copies, unlike the runs of a change (C119). Its limits are still composed in the Workbench's screens rather than its backend. (seen in code)
- In a single-repo system Kata decides by itself that apps build one at a time and which goes next, rather than following the plugin's own answer; the plugin also refuses a second app, so the two rules can drift apart. The engineer says this is a bug: Kata should follow the plugin's answer (C151). (confirmed by engineer)
- Starting a change, renaming it and removing its copy are not refused while its workspace is being migrated (C155); the other runs are. (seen in code)
- Every home load runs one extra dry run of the plugin's migration, and Kata tells "no workspace set up" from a real failure by matching the plugin's English message, which the plugin does not list as stable. (seen in code)
- A plan with no tasks shows as "build finished"; neither Kata nor the plugin's build gate stops on it. (seen in code)
- A full-pipeline change whose generated name (date plus first five words) already exists is refused with a general message; the engineer has to reword the description. (seen in code)
- Kata keeps its own check of an intent's scope (anything that fits a commit header), which differs from the plugin's scope check (letters, digits, dots, underscores and hyphens, at most 64); it only picks the default sent to the plugin. (seen in code)
- Kata's findings and round types know a "critical" severity that the plugin's finding format never carries. (seen in code)
- A branch renamed by hand outside the Workbench is reported as missing; Kata looks only for the recorded name. (seen in code)
- The view of what changed compares against the remote's base branch, so commits sitting on the local base that were never pushed show up as part of the change, while the plugin's definition of touched leaves them out. A repository whose only difference is such commits can be listed in the view yet gets no pull request. (seen in code)
- The checks results Kata shows are the plugin's record on this machine; another engineer's machine has its own. (seen in code)
- After a rename, pull requests opened from the old branch name stay open on GitHub and stay recorded; Kata lists them for the engineer to close and never closes them. (seen in code)
- Links inside rendered documents (intent, spec, plan, findings) do not take the pull request links' route (C82). They allow web and mail addresses and ask the page to open a new window, which a newer code comment says the desktop app ignores. The engineer could not say whether document links open in the desktop Workbench; someone needs to try one. (intent unknown)

- A stale comment on the build page still mentions a branch that "needs a name", a step that no longer exists. (seen in code)
- In the single-repo layout, Kata's own, the live list of checks on the base (C159), the stop question and the stopped note (C164) never appear, because an app's build start runs outside the preparation step they hang off. The engineer accepts this as a limitation for now. (confirmed by engineer)
- After a Workbench restart, a build this Workbench started and left under way reads "Started outside this Workbench" as a fact, because the record of which builds ran here is kept in memory only. The engineer accepts this. (confirmed by engineer)
- Some of the build checks' decisions and wording are still made in the screens rather than the backend: whether accepting is off during a preparation, which repository's checks are listed, the "running elsewhere" question's sentences, and the "Running the checks again" label.
