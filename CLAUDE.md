# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Kata is

Kata is a launcher for single, headless coding-agent runs. You compose a *run-spec* (one precise, reproducible form for a job) and Kata runs it by driving `claude -p` to completion and observing it. The task reaches Claude as the first user message on its input, in streaming mode (`--input-format stream-json`), and Kata closes that input once the run begins to end, which is what lets Claude exit after its last result. Kata never owns the agent loop — it rents it via `claude -p` and controls the edges: the empty room (`--bare`, default-on but switchable per run), retasking (an appended/replacing system prompt), a curated kit (a disposable `--plugin-dir`), and the leash (turn cap, wall-clock timeout, optional worktree isolation, exit code).

The `kata` binary is the single execution path the GUI, the Shokunin orchestrator, and CI all share. `README.md` and `ROADMAP.md` carry the product vision and milestone status; design specs and plans live in `docs/superpowers/`.

**Before adding a run-spec field, an event, a CLI subcommand, or a Workbench pane, read [`docs/adding-a-feature.md`](docs/adding-a-feature.md).** Each shape has a regeneration chain that CI gates, and the common failure is getting that chain wrong rather than the code.

## Layout

A Cargo workspace plus a Tauri app. Four crates in `[workspace].members`:

- `crates/kata-core` — the engine library (`kata_core`). Also builds the `fake-claude` test binary. Modules: `spec` (the `RunSpec` contract: TOML/JSON load/save + pure `validate`), `catalog` (`discover` skills/plugins from user+project scopes, plus the embedded builtin kit), `builtin` (the repo's `.claude/plugins/kata/` workflow plugin, embedded at build time by `build.rs` and materialized under `<kata-home>/builtin/` so `[plugins.kata]` resolves in any workdir; user/project plugins of the same name shadow it), `command` (`build_invocation` pins the exact claude flag set), `assemble` (build the disposable `--plugin-dir` with RAII temp cleanup), `ask` (the localhost bridge and the `mcp-ask` MCP server behind the `ask_user` and `approve_tool` tools), `run` (orchestrate the child, stream `KataEvent`s, enforce the leash, clean up), `event` (the normalized `KataEvent` protocol + `parse_stream_line` translating claude `stream-json`), `permission` (rule *syntax* validation and call-target rendering for `[permissions] mode = "prompt"` — it does not match rules; claude does, from a generated settings file), `given` (the items a run starts with: identity and parsing of `[given]` entries, `resolve` for the preview the Workbench shows before a run, `apply` for the claude flags and settings a switched-off item turns into, `status` for the verdict on the `run.given` event, and `lock` for the items that cannot be switched off), `bundle` (`kata bundle`: vendor a spec's kit into a portable folder), `changeset` (the git changeset behind `run.diff`), `worktree` (`leash.isolation = "worktree"`, made in process with `git2`; it refuses a repository whose filters or signing need an external program, through `hooks::needs_external`), `hooks` (runs a repository's git hooks the way git does, for the commits, switches and worktrees Kata makes itself), `proc` (the one way to start a child process, see "Child processes" below), `git` (the libgit2 jobs the engine and `kata-sdlc` share: `file_counts`, `index_stamp`, `smudge_racy_entries` and `hash_file`), and the Workbench's file-backed libraries `history` (past-run transcripts as `RunRecord`s), `katas` (saved run-specs) and `presets` (context presets), plus `fsutil`.
- `crates/kata-sdlc` — the AI-SDLC mode backend library (`kata_sdlc`). The ai-sdlc plugin owns the change workflow; this crate asks it and shows its answer, and decides only what the plugin does not. Modules: `ai_sdlc` (the one door to the plugin's program, `node <plugin>/tools/ai-sdlc.ts`, through `Program` and its typed answers `state`, `status` and `show`; every call goes through it, hidden and time-limited), `plugin` (what the machine needs: `MIN_VERSION` 1.1.0, the plugin floor, below which the mode is blocked, `MIN_NODE` 22.18, and git and gh found on `PATH`), `offer` (a change's stage, label and actions, decided from the plugin's `state` answer and the few live facts only the Workbench has), `view` (what the home and change pages read), `permissions` (the deny rules of a run of a change, built here: `rule_path` is the one owner of the rule shape), `runspec` (the run-spec of a run of a change), `holds` (which change holds which product repository while it builds or reviews), `coordinator` (the build's rules as a pure state machine: which repositories run, when one stops, when a round is done and when the review starts), `round` (the round offer, the default picks and the review rows), `accept` (accepting and rejecting a change's documents: Kata edits one front matter line, the plugin commits and runs the event), `copy_removal` (the offer to remove a finished change's copy and the plugin's `change remove` behind it), `checks_view` (what a repository's checks came to, read from the plugin's ledger and hook list), `old_checks` (the per-machine list of checks that earlier versions kept, read only to tell the engineer once), `done` (declaring a change done: the plugin's `change.done` verifies, pushes and opens the pull requests), `pull_requests` (the pull requests a change was declared done with, from `change.yml` first, else from `prs`), `prs` (the record `pull-requests.json` held before the plugin recorded them; read only), `build` (`build::status`, which reads `plan.md` tasks and `build/<repo>.md` rows through the format program), `changes` (a change's documents read from the master's working tree, and the name checks), `format` (the plugin's format program for reads, with the parse cache at `<kata home>/workbench/parse-cache/`; a `Shown` read uses the cache, a `Gate` read always asks the program), `review` (the review document `build/review.md`), `naming` (a system's naming setting, read only through the program's `naming`, `branch-name` and `scope` commands), `workspace` (workspace scanning), `branch` (reads and the checkout around a run: `branch_info`, `change_branch`, `heads`, `missing_change_branches`), `snapshot` (what the master looked like before a run and what the run left behind), `diff` (the Changes view's comparison, the base branch read from local refs and never fetched, `commit_files` and `change_repos`), `git` (repository reads with libgit2), `frontmatter` (front matter reads), `store` (the local `<KATA_HOME>/workbench/` JSON data, including the append-only `task-runs.json` that links each recorded task to the run that recorded it, through `load_task_links` and `append_task_links`) `process` (how a finished child ended) and `testutil` (git fixtures, compiled for tests only). It never touches the run-spec or the event protocol; the Workbench backend links it in-process.
  The plugin floor is 1.1.0 (`plugin::MIN_VERSION`) and the program needs Node.js 22.18 or later. The AI-SDLC mode needs `git` and `gh` on `PATH`, because the plugin starts them for commits, pushes and pull requests as the engineer; the Workbench mode needs neither. Kata's own branch, commit, push, hook and GitHub code for this mode is gone, and where the plugin and Kata disagree the plugin wins. A vendored copy of the plugin's `tools/` lives in `crates/kata-sdlc/tests/ai-sdlc-tools/` so tests and CI never need the plugin repository; after the plugin floor changes, refresh it with `node scripts/vendor-ai-sdlc-tools.mjs` (line endings are normalized to LF, matching `.gitattributes`). `format_conformance` also compares the copy with the sibling `../ai-sdlc/plugin`, but only where that checkout exists; CI has no sibling, so it runs against the vendored copy alone.
  Checks are the team's `build.finish` hooks, committed to the master repository and run by the plugin when a repository's build finishes; Kata runs none and keeps no list of its own. Each change runs in its own copy of the master repository, `<workspace>/.ai-sdlc/copies/<change>`, which is why several changes run at once. The Workbench backend in `app/src-tauri/src/` holds what the crate cannot: `build_host` (one build per change, run in the backend: the page reads its `BuildState` and the build survives the page), `runs` (the table of live runs and the claim rule), `history` (every live run's events from its start, so a screen opened late replays the whole run), `running` (the running-changes strip: one entry per change that works or needs the engineer, with `opens` saying what picking it opens), `close_guard` (closing the Workbench asks first, naming every running change, and cancels them all on a confirm: `CloseOutcome`), `start_change`, `rename_change` and `sdlc_state`.
  The claim rule, in `runs.rs`, by lane. A run is on the `Solo` lane (the Workbench, the library: outside any workspace) or on a `Change` lane (a run of one change, `build` true for a build run). Never two runs in one folder, on any lane. A `Change` lane is refused while its copy is being removed. Two `Solo` runs never overlap. Different changes never block each other on the table, and the build host's holds add the one more limit: a product repository is held by at most one change at a time for its build and its review, taken for every repository a build needs at once or not at all, in memory only. A change started before copies existed lives in the engineer's checkout of the master, so two such changes run one at a time.
- `crates/kata-cli` — the `kata` binary. Thin CLI over `kata-core` with five subcommands: `init`, `validate`, `catalog`, `run`, `bundle`, plus a hidden `mcp-ask` that every run depends on for `ask_user` (claude launches it as `<current exe> mcp-ask`).
- `app/src-tauri` — the Workbench desktop backend (`kata-app`). See "The Workbench" below.

`examples/katas/` holds version-controlled reference run-specs (the superpowers brainstorm → plan → execute trio) with a README; they are documentation, not seeded at runtime.

## Where logic lives

Rust is the brains; the Workbench frontend is presentational. Every rule a spec, a context file or a decision table states is computed in `kata-sdlc` or `kata-core` and reaches the frontend as data through a Tauri command; a TypeScript ViewModel only filters, folds, formats and holds form state. A preview and the action it previews use the same Rust call, a command that the frontend needs for several items takes a list, and an operation across several repositories checks them all before it changes any. The full policy, with the decision test and the one remaining piece of TypeScript logic recorded as debt, is the `kata-architecture` skill (`.claude/skills/kata-architecture/SKILL.md`). Read it before deciding where a piece of behavior is computed.

## Child processes

Every child process in the workspace starts through `kata_core::proc::hidden_command`, which sets `CREATE_NO_WINDOW` on Windows so the Workbench never flashes a console window. `clippy.toml` bans `std::process::Command::new` and `tokio::process::Command::new` (`disallowed-methods`), so `cargo clippy --all-targets -- -D warnings` fails on a direct spawn; the only allow is inside `new_hidden`, the one place `CREATE_NO_WINDOW` is set, behind `hidden_command` (which `run_limited` starts through too). `hidden_command` refuses `git` and `gh` as programs (`SpawnRefused`) with no opt-out: checks are the plugin's hooks now, so Kata starts no program the engineer chose. Kata's own flows start nothing but `node` (the plugin's program, which starts `git` and `gh` itself): the `no_git_programs` tests run the Workbench's flows with `PATH` holding only `node` and the `kata` binaries, so any flow that still starts `git` or `gh` by name fails, and `kata_core::proc::SpawnLog` is the test hook that records every program a flow starts. `kata_core::proc::run_limited` is the one time-limited runner (it kills the whole process tree on a timeout and keeps a bounded output tail); hooks and the ai-sdlc program use it. `process-wrap` is a unix-only `kata-core` dependency; on Windows the tree is killed through a job object (`windows-sys`). The opener plugin behind `open_url` was checked and needs no change: it calls `ShellExecuteExW` in process (`open` 5.3.5 with `shellexecute-on-windows`), which starts no console program.

The Workbench mode needs neither `git` nor `gh` installed; the AI-SDLC mode needs both on `PATH`, since the plugin starts them. The tests need `git` too: the parity tests in `kata-sdlc` and `kata-core` use the `git` command as an oracle, so `cargo test --workspace` needs `git` on `PATH`, and Node.js 22.18 or later for the ai-sdlc program.

## Two contracts that cross language boundaries

These are the stable, language-neutral interfaces; `kata-core` is the reference implementation but the contract is not Rust-specific (Shokunin is .NET and consumes both).

- **The run-spec** (`spec::RunSpec`) — what to run. Serialized to TOML/JSON.
- **The event protocol** (`event::KataEvent`) — `run.started` / `assistant.text` / `tool.use` / `tool.result` / `turn` / `log` / `run.completed` / `run.error` / `run.cancelled` / `ask.requested` / `ask.answered` / `permission.requested` / `permission.decided`, one JSON object per line on the engine's stdout. `ask.requested` carries the question list and a correlation `id`; `ask.answered` carries the same `id` and the `answers: string[][]` — on any run, interactive or not, since every run gets the `ask_user` tool. The `permission.*` pair appears only under `[permissions] mode = "prompt"` or `"auto"`. `permission.decided` is emitted only for a check that reaches Kata's own tool — the `unmatched` policy, the operator, or one of Kata's own bridge tools (`decided_by: "engine"`); a call claude's settings resolve (its own `allow`/`deny`, or its built-in read-only auto-approve) is never seen by Kata and gets no event at all. `permission.requested` is emitted only for one that pauses the run on the operator.

`RunSpec` and the catalog/enum types are mirrored to TypeScript in `app/src/bindings/` by **ts-rs**, gated behind the `ts` Cargo feature. After changing any of these types, regenerate: `cargo test -p kata-core --features ts export_bindings`. Do not hand-edit `app/src/bindings/`.

The **run-spec** is also published as a JSON Schema at `schema/kata-runspec.schema.json`, generated from `RunSpec` via `schemars` (gated behind the `schema` Cargo feature) and stamped with `specSchemaVersion`. Regenerate after changing any run-spec type: `KATA_BLESS_SCHEMA=1 cargo test -p kata-core --features schema runspec_schema_artifact_is_fresh`. It is primarily an authoring aid (editor autocomplete via the `#:schema` directive that `kata init` embeds); CI fails on drift, same as the event schema.

The **event protocol** is published as a JSON Schema at `schema/kata-events.schema.json`, generated from `KataEvent` via `schemars` (gated behind the `schema` Cargo feature) and stamped with `protocolVersion`. Regenerate after changing any event type: `KATA_BLESS_SCHEMA=1 cargo test -p kata-core --features schema schema_artifact_is_fresh`. The Workbench's TS event types (`app/src/bindings/kata-events.ts`) are generated from that schema with `cd app && npm run gen:events`; `app/src/lib/events.ts` re-exports them and adds hand-written render/status helpers. CI fails on drift in either direction.

The `kata-sdlc` types the frontend reads (`Settings`, `WorkspaceEntry`, `ChangeInfo`, `Snapshot`, `Leftovers`, and friends) are mirrored to `app/src/bindings/` the same way: `cargo test -p kata-sdlc --features ts export_bindings`. Do not hand-edit them.

The `kata-app` types the frontend reads (`ChangeRef`, `StartOutcome`, `BuildEvent`, `RunningStrip`, `CloseOutcome`, `HistoryEntry`, and friends) are mirrored the same way: `cargo test -p kata-app --features ts export_bindings`. Do not hand-edit them.

## Exit-code semantics (the leash)

The engine maps run outcomes to process exit codes, and the CLI surfaces them: turn cap → **125**, wall-clock timeout → **124**, answer deadline exceeded → **123**, budget ceiling reached → **122**, cancel → **130**. The CLI itself uses **1** for validation failure and **2** for load/parse error. Preserve these — they are part of the CI/orchestrator contract. Exit 123 is reached when an operator wait exceeds `answer_timeout_secs`, or at once when nobody can answer (the engine's answer channel is closed — kata-cli's stdin at EOF); it is distinct from 124 so CI logs can tell "work ran too long" from "nobody answered." Exit 122 is reached only when `leash.max_budget_usd` is set and claude stops on its native `--max-budget-usd` (a post-turn check, so the actual spend can overshoot the ceiling by up to one turn); the engine detects the `error_max_budget_usd` result subtype and overrides claude's generic exit 1. Exit 125 is only reachable when `leash.max_turns` is set; an unset cap means unlimited turns, bounded only by the wall-clock timeout (exit 124). Exit 123 covers both kinds of operator wait — an unanswered `ask.requested` and an undecided `permission.requested`.

## Permissions

A run's permission posture is explicit and never inferred. `[permissions] mode` is `bypass` by default (`--dangerously-skip-permissions`, what every run did before the field existed); `prompt` swaps that flag for `--permission-prompt-tool mcp__kata-ask__approve_tool`, which is the route on a machine whose managed settings set `permissions.disableBypassPermissionsMode`. **There is deliberately no automatic fallback between these modes** — a run whose safety posture changed silently between machines is not reproducible.

Kata does not match rules. Under `mode = "prompt"` the spec's `allow`/`deny` are written verbatim into a generated claude `--settings` file, and claude enforces them itself — before it would ever consult the prompt tool, and before its own built-in read-only auto-approve (`git status`, `git log`, `ls`, `cat`, …). That means a `deny` rule reaches even a read-only command, which an engine-side matcher never could, because it never saw those calls at all. `--permission-prompt-tool mcp__kata-ask__approve_tool` only carries the `unmatched` policy: a call settings don't resolve comes back to Kata, which applies `unmatched` (`deny`/`allow` resolve immediately, `ask` pauses on the operator). `permissions.unmatched = "ask"` requires `[interactive] enabled = true` and `validate` rejects the combination otherwise, since nothing else could answer.

`mode = "auto"` passes `--permission-mode auto` alongside the same `--permission-prompt-tool`, handing every call its `allow`/`deny` rules don't resolve to claude's own built-in classifier in place of Kata's `unmatched` policy. The classifier auto-approves routine work and blocks the destructive or externally-reaching call on its own judgment. `permissions.allow` and `permissions.deny` are still written to the settings file and enforced by claude before the classifier ever runs — a `deny` blocks a matching call, an `allow` pre-approves one — exactly as under `prompt`. `permissions.ask` is the operator's only entry point under `auto`: a matching call is routed to Kata's `approve_tool` bridge and pauses the run. Under `prompt` an `ask` rule does not pause by itself (a call that reaches Kata's tool is settled by `unmatched`), but `validate` still requires `[interactive] enabled = true` for a non-empty `ask` list under either mode. `unmatched` has no meaning under `auto`, since the classifier is itself the unmatched handler; `validate` rejects a spec that sets `mode = "auto"` together with `unmatched = "deny"` or `"allow"` (it compares against the default, so `"ask"` passes). The classifier's own tuning knobs (an `autoMode` settings block for `environment`, `soft_deny`, `hard_deny`) are out of scope for now, so every `auto` run currently gets claude's conservative built-in defaults.

The AI-SDLC build always runs under `mode = "auto"` with generated deny rules, whatever the permission setting elsewhere, because the bypass posture cannot carry deny rules. The rules are built in Rust by `kata_sdlc::permissions` (`rules`, with `rule_path` as the one owner of the shape; `runspec` composes them into the run-spec), and on Windows claude only honors them in one shape: `Edit(path)` rules (a `Write(path)` rule is ignored; `Edit` covers every editing tool) with the path in the colon-less, lowercase-drive form, so `D:\ws` becomes `//d/ws`. A `D:/ws` or `Write(...)` rule is silently not enforced. The proofs are in `crates/kata-core/tests/run_it.rs`; do not change the rule shape without re-running them. The rules cover claude's editing tools; a write made from a shell inside a run is not covered by them, an accepted gap (the plugin's guard covers shell commands only for the paths it guards).

Permission mode governs tool *approval*, not whether claude asks questions — under `bypass` and `auto` the model still reaches for its built-in `AskUserQuestion` at a fork, and headless that call kills the session outright. So on **every** run, whatever the mode and whether or not `[interactive]` is on, `command::build_invocation` passes `--disallowedTools AskUserQuestion` and `run` wires Kata's `ask_user` tool plus its retasking note. A question always pauses on the operator — there is no automatic answer; `answer_timeout_secs` bounds the wait, and a run whose answer channel is closed exits 123 immediately rather than hanging with its work clock paused. `[interactive] enabled` now only decides whether *permission checks* may pause on the operator. Do not gate `ask_user` or the disallow on interactivity again.

## The Workbench (`app/`)

A Tauri v2 desktop app: Angular 22 SPA frontend (`app/src/`, the angular-jig template, SpartanNG primitives, TypeScript) over a Rust backend (`app/src-tauri/`). Layout A: compose the run-spec on the left, observe the run on the right. The routes are `` (the Workbench) and `/library`. A second mode, AI-SDLC, lives on four more: `/mode` (pick the mode), `/sdlc` (workspace home), `/sdlc/:system/context/:repo` (one product repo's context file, read-only; its Run or Refresh context hands the repo back to the home page as `?context=<repo>`, which owns the run) and `/sdlc/:system/:change` (one change), whose page carries the intent, spec, plan and Build tabs, with the Changes view, the review findings and the pull requests inside the Build tab rather than on routes of their own. Its runs go through the same `run_spec` sidecar path; the frontend side is `core/sdlc/sdlc-runner.ts`, `core/lock/lock.store.ts`, `core/run/change-run.store.ts`, `core/run/run-landing.store.ts` and the `sdlc-*` mock fixtures in `app/src/app/lib/sdlc-mock.ts`.

The backend splits its relationship with the engine deliberately (see `app/src-tauri/src/lib.rs`):

- It **links `kata-core` in-process** for the cheap, pure operations — `catalog`, `load_spec`, `save_spec`, `validate_spec` are `#[tauri::command]` one-liners over the library.
- It tracks every live run in a table (`app/src-tauri/src/runs.rs`), so several runs can be live at once. `run_spec` takes an optional `group` (`build:<system>/<change>`) next to the run-spec, never inside it, and refuses any run outside the build while a build run is live.
- It **spawns the `kata` sidecar binary** for the one impure operation, `run_spec`: serialize the spec to a temp file, spawn `kata run` in the spec's workdir, and relay its JSON-line `KataEvent`s to the webview over the `kata://event` channel. `cancel_run` writes a `cancel` line to the engine's stdin (the engine traps it, kills claude, cleans up, emits `run.cancelled`), falling back to a hard kill. This keeps the GUI on the engine's single execution path.

The frontend stays **presentational**. Every backend call goes through the abstract `KataTransport` (`app/src/app/core/transport/`): `provideKataTransport` picks `TauriTransport` (`invoke`/`listen`) under Tauri and `MockTransport` (fixtures and a scripted run timeline from `app/src/app/lib/mock.ts`) in a plain browser, once at bootstrap. `RunStore` (`app/src/app/core/run/run.store.ts`) folds the relayed `KataEvent`s into run state; each routed screen is a thin component over a component-scoped ViewModel that reads the stores and calls the transport.

**Design rules are non-negotiable and live in `app/CLAUDE.md`** (the dark "sumi-ink" system, single Hanada-azure accent, IBM Plex type, andon status palette). Read it before touching anything visual. Style only against CSS custom properties — never hard-code a hex value. The full system + per-component specs are in `design/README.md`; pixel references in `design/prototype/` are HTML/React — recreate in Angular, never copy.

## Commands

Rust (run from repo root):

- Build: `cargo build --locked`
- Test the engine: `cargo test -p kata-core -p kata-cli` — no prerequisites, and it is what you want for engine work.
- Test the workspace: `cargo test --workspace` **needs the sidecar staged first** (`node app/scripts/stage-sidecar.mjs`, or `cd app && npm run sidecar`). The `kata-sdlc` tests run the vendored ai-sdlc program, so they also need Node.js 22.18 or later on `PATH`. `app/src-tauri` declares the `kata` binary as a Tauri `externalBin`, so its build script fails with `resource path binaries\kata-<target-triple> doesn't exist` on a clean checkout. CI stages it before this step; do the same locally.
- A single test: `cargo test -p kata-core <name>` or `cargo test -p kata-cli --test cli_it <name>`
- Test as CI sees the machine: `node scripts/test-clean-home.mjs --workspace` runs `cargo test` with `HOME` and `USERPROFILE` pointed at an empty folder under `target/` and `KATA_HOME` cleared, so a test that passes only because this machine has a plugin, a skill or a Kata home installed fails here instead of on CI. It takes any `cargo test` arguments. Run it before pushing a test that reads the catalog or the Kata home. It is not a cargo `[env]` setting on purpose: that would also empty the home for `cargo run` and `npm run tauri:dev`.
- Format (must be clean; **CI gates this**): `cargo fmt --all --check` (run `cargo fmt --all` to fix). Note it is workspace-wide, so it can surface pre-existing drift in files you did not touch.
- Lint (must be clean): `cargo clippy --all-targets -- -D warnings`
- Regenerate TS bindings after type changes: `cargo test -p kata-core --features ts export_bindings` (writes `app/src/bindings/`; the event types there come from `npm run gen:events`, below)

App (run from `app/`):

- Browser dev (fixtures, no native backend): `npm start` → `http://localhost:1420`. `http://localhost:1420/?demo=run` auto-starts the scripted Observe-pane run for screenshots.
- Real desktop app with the live engine: `npm run tauri:dev` — this first stages the `kata` sidecar (`scripts/stage-sidecar.mjs` builds `kata-cli` and copies it to `src-tauri/binaries/kata-<target-triple>`), then launches Tauri. A real run needs an authenticated `claude` on PATH.
- Lint (the house rules, ESLint) and the CSS token gate: `npm run lint`, `npx stylelint "src/**/*.css"`
- Production build: `npm run build` (outputs to `app/dist/angular-jig/browser`, which Tauri's `frontendDist` serves)
- Frontend tests: `npm test -- --watch=false` (Vitest through `ng test`)
- Regenerate the TS event types from `schema/kata-events.schema.json`: `npm run gen:events`
- Browser gates (need Playwright Chromium): `npm run check:boot` (every route renders), `npm run check:interaction` (every overlay opens and closes), `npm run check:parity` (pixel diff against the frozen baseline in `app/parity/baseline/`; local only, the baseline is Windows-rendered), `npm run check:responsive` (1280 and 1600 for every route, plus the change page toolbar, the workspace home, the pull request popover and the Build strip, through `scripts/check-change-toolbar.mjs`, `check-home-page.mjs` and `check-doc-layout.mjs`; the Build strip is also measured at 768, 1024 and 1440), `npm run check:changes` (the Monaco diff editor under the desktop CSP, zoom and widths), `npm run check:build` (the build page at 1280 by 800 against the scripted build, `?demo=build-long`), `npm run check:start-flow` (the light track: fix routes, New change with the Track field, the scripted triage at `?demo=start`), `npm run check:wiring` (fails on a public ViewModel or component member no template references), `npm run screenshots` (capture the README and release images)

## Testing notes

- The engine's integration tests drive the offline `fake-claude` binary via the `KATA_FAKE_MODE` env var (`crates/kata-core/tests/run_it.rs`). These tests mutate process-global env and are marked `#[serial]`; don't remove that.
- The opt-in real-claude smoke test asserts a genuinely successful run, so it needs an authenticated `claude` on PATH. It runs only when `KATA_SMOKE_REAL` is set; unset it skips.
- Per the roadmap workflow: TDD, `cargo fmt --all --check` and clippy clean, `cargo build --locked` green, frequent commits on a `feat/<milestone>` branch.
