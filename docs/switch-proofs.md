# Switch-off proofs

Which ways of leaving an item out of a run actually work on a real Claude Code. The proofs are in `crates/kata-core/tests/switch_proofs.rs`; run them with `KATA_SMOKE_REAL=1 cargo test -p kata-core --test switch_proofs -- --nocapture --test-threads=1` on a machine with an authenticated `claude`. Without the variable every test skips.

All rows were run against Claude Code 2.1.308 (haiku, bypass permissions, `--include-hook-events`, which the installed claude accepts). A row that did not hold is marked "unproven: ships locked", and the item kind it covers is locked in `SWITCHABLE` (T2).

| Mechanism | Claude Code | Held | Observed |
|---|---|---|---|
| Hook, project source: drop `project` from `--setting-sources`, pass the rest in `--settings` | 2.1.308 | yes | Project hook A switched off, hook B of the same source kept (via `--settings`), local hooks kept: markers A absent, B, C, D present. Other project content passed in the file (`outputStyle`) took effect. |
| Hook, local source: drop `local`, pass the rest in `--settings` | 2.1.308 | yes | Local hook C off, D kept, project hooks kept: markers A, B, D present, C absent. |
| Hook, personal source: drop `user` | 2.1.308 | yes, with a caveat | The machine's personal hooks stopped firing: `hook_started` lines went from 11 to 4 (only the four project and local hooks). The personal hook content was not re-routed in the test, because the real personal settings are never written; the mechanism is the same as for project and local. |
| Plugin, installed: `enabledPlugins: { "<name>@<marketplace>": false }` | 2.1.308 | yes (user scope) | `ai-sdlc@ai-sdlc` was in the start report's `plugins` before, absent after, and its six skills disappeared from `skills` too. Project-scope installs are bound to a `projectPath` and cannot be exercised from a temporary folder, so project scope is untested; the key is the same. |
| Standing instruction, any `CLAUDE.md` or rules file: `claudeMdExcludes: [<absolute path>]` | 2.1.308 | yes | A project `CLAUDE.md` and a `.claude/rules/r.md` each told the model to end its reply with a nonce. The baseline reply carried both; with both paths excluded (forward-slash absolute paths) neither appeared. The personal `~/.claude/CLAUDE.md` was not tested, because it would need a marker written into the real home; the mechanism is path-based. |
| Standing instruction, output style: `outputStyle: "default"` | 2.1.308 | yes | The start report's `output_style` read `Explanatory` from project settings and `default` with the per-run setting. |
| Tool server: `--strict-mcp-config --mcp-config <file>` holding only the kept servers | 2.1.308 | yes | Two servers (`srv-a`, `srv-b`, both `kata mcp-ask`) in `.mcp.json`: with a file holding only `srv-a`, the start report listed only `srv-a`, status `connected`. Side effect: the report also lost all nine plugin tool servers (`plugin:...`) and all four claude.ai connectors. Strict mode removes every tool server not in the file, so a plugin's tool servers do not survive it. |
| Skill, on disk: `permissions.deny: ["Skill(<name>)"]` | 2.1.308 | unproven: ships locked | The skill stays in the start report's `skills`. When invoked, the call is refused (`permission_denials` lists it, and the model says it was blocked). A deny rule refuses the skill; it does not remove it, so R15.1 would read "switched off, but Claude loaded it". |
| Settings re-routing keeps the model (area of concern 2) | 2.1.308 | yes, only when the dropped source is the only one that sets the value | Project `model = haiku`: the start report's `model` was the same with and without re-routing. When local also sets `model = sonnet`, the baseline is sonnet (local overrides project) but the re-routed run is haiku: `--settings` outranks the local source, so a value re-routed from a lower source beats a kept higher source. A personal value was not tested (the real home is never written); `--settings` also outranks personal, so the same inversion applies in the other direction. |

## Other observations

- Dropping the `project` source also drops that source's `CLAUDE.md`, rules files, project skills and `.mcp.json` tool servers. The report shows no `projskill`, no `srv-a` or `srv-b`, and neither nonce. Anything the user wants to keep from that source must be re-supplied (`--settings`, `--mcp-config`) or it is gone with it.
- Dropping the `user` source also drops every non-builtin plugin (the report listed only the three builtin ones), while project skills and `.mcp.json` tool servers stayed. The `claude.ai` connectors stayed too.
- Resolver consequence of the precedence finding: for scalar settings (`model`, `outputStyle`, `permissionMode`) the per-run file must carry the effective value (already merged across the kept sources), not the dropped source's own value, or it overrides a kept source that should win.
- A temporary `CLAUDE_CONFIG_DIR` breaks authentication (`terminal_reason: api_error`, zero tokens) because the login lives in the real config. Every proof therefore runs against the real home, read-only, from a temporary project folder; the only side effect is session transcripts under the real `~/.claude/projects`.
- `--include-hook-events` emits `system` lines with `subtype` `hook_started` and `hook_response`, each with `hook_id`, `hook_name`, `hook_event` and `session_id` (the response adds `output`, `stdout`, `stderr`, `exit_code` and `outcome`). Captured in `crates/kata-core/tests/fixtures/claude-hook-events.jsonl`. The `system`/`init` line is in `crates/kata-core/tests/fixtures/claude-init.json`.
- The start report's `plugins` entries carry `name`, `path`, `source` (`<name>@<marketplace>`, or `<name>@builtin`) and, for installed ones, `version`; `mcp_servers` entries carry `name`, `status` and `source`.
