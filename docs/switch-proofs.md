# Switch-off proofs

Which ways of leaving an item out of a run actually work on a real Claude Code. The proofs are in `crates/kata-core/tests/switch_proofs.rs`; run them with `KATA_SMOKE_REAL=1 cargo test -p kata-core --test switch_proofs -- --nocapture --test-threads=1` on a machine with an authenticated `claude`. Without the variable every test skips.

Rows marked 2.1.308 were run against Claude Code 2.1.308, rows marked 2.1.309 against 2.1.309 (haiku, bypass permissions, `--include-hook-events`, which the installed claude accepts). A row that did not hold is marked "unproven: ships locked", and the item kind it covers is locked in `SWITCHABLE` (T2).

| Why a synced plugin's tool server (`design` / `asana`) is in a re-supplied run but not in the normal run | 2.1.309 | explained, reproducible | Cause, from the normal run's debug log (`--debug-file`): `Left out MCP server "asana" of synced plugin design: its last sign-in attempt found no way for a terminal to register (GrowthBook flag tengu_starry_locket)`. The rule applies only to plugins whose source is `synced`; the same folder passed with `--plugin-dir` is `@inline` and keeps every server. It is not a personal setting (no MCP key in `settings.json`, none in `~/.claude.json`), not a different file (the normal run loads the same `design~g2` folder), and not a claude.ai connector dedupe (`claude mcp list` shows no Asana connector, and with all sources kept an inline `design` still lists asana). Rule as read from the binary: the plugin is synced, the cached flag `cachedGrowthBookFeatures.tengu_starry_locket` in `~/.claude.json` is true, the server is `http` or `sse` with no `oauth.clientId`, no `${` in its URL and no user info, and `~/.claude/.credentials.json` holds a `plugin:<plugin>:<server>|<hash>` record with no token, no `clientId`, `discoveryState.oauthMetadataFound` true and `discoveryState.registrationNotOfferedAt` within the last 30 days (older records are rechecked, so the set changes with time). The test recomputes that rule from those two files (metadata only) and it matched the log. A generated copy of the plugin whose `.mcp.json` omits the left-out servers gave the same `plugin:design:*` server names as the normal run; the order followed the file, so keep the key order of the original `.mcp.json` when rewriting it. |

## Other observations

- Dropping the `project` source also drops that source's `CLAUDE.md`, rules files, project skills and `.mcp.json` tool servers. The report shows no `projskill`, no `srv-a` or `srv-b`, and neither nonce. Anything the user wants to keep from that source must be re-supplied (`--settings`, `--mcp-config`) or it is gone with it.
- Dropping the `user` source also drops every non-builtin plugin (the report listed only the three builtin ones), while project skills and `.mcp.json` tool servers stayed. The `claude.ai` connectors stayed too.
- Resolver consequence of the precedence finding: for scalar settings (`model`, `outputStyle`, `permissionMode`) the per-run file must carry the effective value (already merged across the kept sources), not the dropped source's own value, or it overrides a kept source that should win.
- A temporary `CLAUDE_CONFIG_DIR` breaks authentication (`terminal_reason: api_error`, zero tokens) because the login lives in the real config. Every proof therefore runs against the real home, read-only, from a temporary project folder; the only side effect is session transcripts under the real `~/.claude/projects`.
- `--include-hook-events` emits `system` lines with `subtype` `hook_started` and `hook_response`, each with `hook_id`, `hook_name`, `hook_event` and `session_id` (the response adds `output`, `stdout`, `stderr`, `exit_code` and `outcome`). Captured in `crates/kata-core/tests/fixtures/claude-hook-events.jsonl`. The `system`/`init` line is in `crates/kata-core/tests/fixtures/claude-init.json`.
- The start report's `plugins` entries carry `name`, `path`, `source` (`<name>@<marketplace>`, or `<name>@builtin`) and, for installed ones, `version`; `mcp_servers` entries carry `name`, `status` and `source`.
- Running these proofs against the real home leaves traces made by Claude Code itself, not by the test code: session transcripts under `~/.claude/projects`, empty `~/.claude/plugins/data/<name>-inline` folders, `<name>@inline` ids in `~/.claude.json` (`pluginUsageLspGraceAppliedIds`, `mcpNeedsAuthNoticed`), and sign-in discovery records for the probed `plugin:<name>:<server>` servers in `~/.claude/.credentials.json` (`registrationNotOfferedAt` timestamps, no tokens).
